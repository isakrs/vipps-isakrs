Open with the mental model: this is not just a schema. It is an operating envelope. The product configuration is intentionally small, but the platform expands it into everything a team needs to build and run safely.

Environment aware

Shared execution

This slide is the platform flow. The important bit for Data Insights is that product teams do not need to know the full set of Azure and Databricks primitives. They declare the product. The platform materializes the primitives.

4. Network controls

The storage firewall starts closed, then opens only explicit paths.

Vipps virtual private networkAllowed address ranges support interactive administration and controlled human access.
GitHub ActionsDeployment runner address ranges are allowed for infrastructure and bundle deploys.
Publication recipientsDelta Sharing recipient address ranges are added when external publication is configured.
Storage account firewall Default action is deny. Azure services bypass is enabled, and every allowed path is generated from platform configuration.
Workspace subnetsClassic compute reaches storage through the Databricks workspace private and public subnets.
Network connectivity configurationServerless compute and serverless warehouse traffic use private endpoint rules.
Blob and Data Lake endpointsPrivate endpoint rules are created for both blob and dfs storage endpoints.
Serverless detail

The warehouse is not inside the classic workspace subnets.

That is why the module attaches private endpoints through the Databricks network connectivity configuration.

External detail

Recipient access is reflected back into the firewall.

Publication configuration produces recipient address rules, so shared data remains reachable without opening storage broadly.

This is one of the more technical slides. The key nuance is that serverless Databricks access needs network connectivity configuration private endpoints, because it does not come from the same subnet path as all-purpose clusters.

7. Grant model

Permissions are role-shaped, not one big owner grant.

Actor Catalog and schema Volumes Workspace folder Runner service principal
Product access group USE_CATALOG, USE_SCHEMA, SELECT READ_VOLUME and WRITE_VOLUME on input_data CAN_READ roles/servicePrincipal.user
Runner USE_CATALOG, USE_SCHEMA, SELECT, CREATE_TABLE, MODIFY READ_VOLUME on artifacts Runtime only Owns job execution context
Deployer USE_CATALOG, USE_SCHEMA, CREATE_TABLE, CREATE_MODEL, CREATE_MATERIALIZED_VIEW WRITE_VOLUME on artifacts CAN_MANAGE roles/servicePrincipal.user
Catalog grants

Catalog access is additive.

The module uses grant resources that do not replace catalog grants owned by the Unity Catalog foundation component.

Schema grants

Schema access is authoritative.

The product schema is owned by the product module, so Terraform can manage the full grant set there.

This is where governance becomes concrete. The product group can read and use the runner, the runner can write product tables, and the deployer can create product assets without becoming a broad platform administrator.
8. Data access views

Views let products depend on source data without copying source grants.

resource "databricks_sql_table" "data_access_view" {
  for_each        = var.config.data_access
  table_type      = "VIEW"
  warehouse_id    = var.serverless_warehouse_id
  view_definition = each.value.query
}
1Terraform creates the view with the platform-owned execution context.
2The view owner can reference underlying source tables.
3Product actors receive SELECT on the product schema.
4Product jobs read the view without direct grants on the source catalog or source schema.
Boundary

Source access stays centralized.

The product sees a stable view contract rather than the raw source permission model.

Compute

Views are created through the shared serverless warehouse.

The deploy stack looks up Serverless Warehouse in the target workspace.

Lifecycle

Queries are configuration.

The view definition moves with the product declaration and is applied by Terraform.

This explains why the product can consume curated sources without direct grants against every source table. The view owner rights model keeps the access boundary tighter.
9. Secrets and notifications

Optional product services are still governed by the same identity model.

Key Vault

akv-dp-<short_name>-<environment>

Created only when product configuration enables secrets or notification destinations.

Azure roles

Runner reads; deployer and group administer secrets.

Runner gets Key Vault Secrets User. Deployer and access group get Key Vault Secrets Officer.

Databricks secrets

Secret scope access mirrors runtime boundaries.

Runner, deployer, and access group get read access through Databricks secret access controls.

Notifications

Slack webhook references become Databricks destinations.

The webhook URL stays in Key Vault; Terraform creates notification destinations from configured secret names.

display_name = "dp-${data_product_name}-${webhook_secret}-${environment}"
destination_type = "SLACK"
url = data.azurerm_key_vault_secret.notification_destination_webhook[webhook_secret].value
Point out that webhook values are not encoded in product configuration. The product owner stores the webhook in Key Vault, and Terraform reads the value when creating the Databricks notification destination.
10. Deployment authentication

GitHub deploys into both Azure and Databricks without stored passwords.

The deployer managed identity receives an Azure federated identity credential, and the Databricks service principal receives a matching GitHub OpenID Connect federation policy.

No long-lived token in repository secrets One deployer per product and environment Repository and environment scoped subject Same product configuration owns both sides

AZURE_CLIENT_ID=<deployer-managed-identity-client-id>

DATABRICKS_AUTH_TYPE=github-oidc

The theme is passwordless deployment. Azure and Databricks have separate federation resources, but both are scoped to the GitHub repository and environment declared for the product.
11. Publication path

Delta Sharing publication is explicit, table-scoped, and network-aware.

1. Product configurationDeclares publication type, recipient metastore identifier, allowed recipient address ranges, and full table names.
2. Share objectTerraform creates a Databricks share containing only configured table objects.
3. Recipient objectDatabricks recipient uses Databricks-to-Databricks authentication and receives SELECT on the share.
4. Firewall updateRecipient address ranges are folded into product storage firewall rules so pre-signed blob access works.
Provider nuance

Share table changes trigger replacement logic.

The module uses a Terraform data resource to recreate the share when table membership changes, avoiding fragile in-place reorder behavior.

Exposure boundary

Publication does not open the product schema.

The share contains only the configured table full names, and recipient network access is scoped through generated address rules.

This slide is useful if someone asks how external sharing stays bounded. The answer is table list plus recipient object plus storage firewall path. Publication is explicit configuration, not a blanket grant.
12. Verification checklist

What I would inspect before calling a product ready.

Layer Check Expected signal
Configuration Short name, owner, schema name, GitHub repositories, optional services. Names satisfy Azure constraints and ownership is unambiguous.
Azure Storage account, container, role assignments, optional Key Vault, firewall rules. Storage is closed by default and only generated actors can read or write.
Databricks Schema, external location, volumes, service principals, workspace folder. Objects exist in the target workspace and catalog with expected grants.
Identity Runner, deployer, access group, GitHub federation, Databricks federation policy. Deployment authenticates with OpenID Connect and workloads run as the runner.
Data access Configured views and their underlying source queries. Runner can select through the view without direct grants to the source catalog.
Publication Delta Sharing recipient, share objects, generated recipient address rules. Recipient can access only configured tables, and storage remains firewall-bound.
